# Assumptions

Generated by `make assumptions` from config/*.yaml. Edit the config notes, not this page.

Every model input is either sourced, with the document it was read from, or a placeholder: a value not read from a cited source, kept visible until something better replaces it. There are 52 placeholders and 32 sourced values.

### connected_solutions.yaml: site_exports

- Value: False
- What and why: Whether a site's battery may export to the grid during events. Export needs an interconnection agreement, and then the 150 percent cap above applies. Without export, the kW curtailed cannot exceed the building's own load in the 3 to 8 p.m. event window, so the model counts per block the lesser of the block's average event output (power times the performance factor) and the building's mean summer weekday event-window load per block, from config/simulation.yaml (event_window, mean_over_peak, times the estimated annual peak). The default assumes no site exports.
- How it gets tested: Ask the operator whether its deployments export during events.
- What would replace it: Each site's interconnection status.

### connected_solutions.yaml: performance_factor

- Value: 0.61 (range 0.61 to 0.92)
- What and why: The share of the battery's 250 kW it delivers on average across an event, since payment follows average kW curtailed. The range comes from the sourced 2 to 3 hour event length (daily_dispatch_terms): the block delivers about 458 kWh (469.8 usable x 0.975), which is 153 kW over a 3-hour event (0.61) and 229 kW over a 2-hour event (0.92). The default assumes 3-hour events. The factor itself is derived, not read.
- How it gets tested: Compare with event performance reported for enrolled batteries.
- What would replace it: The operator's measured event performance.

### connected_solutions.yaml: overlap_factor

- Value: 0.13 (range 0 to 0.13)
- What and why: The share of event days that fall on the building's own monthly peak, when the same battery energy cannot serve both, so grid revenue is not double counted with peak shaving. An upper bound: a building has at most one monthly peak day in each of the 4 event months, and daily dispatch calls at least 30 events (sourced), so at most 4 / 30 = 0.13 of event revenue is at risk. ConnectedSolutions revenue is reduced by this share.
- How it gets tested: Compare event days with simulated monthly peak days on the ComStock sample.
- What would replace it: A joint simulation of events and peak shaving.

### costs.yaml: itc

- Value: rate=0.3, default_on=False, max_capacity_kw=1000
- Source: 26 U.S.C. 48E(a)(2)(B)(ii)(I), energy storage technology with a capacity under 1 MW, as amended by Pub. L. 119-21, https://www.law.cornell.edu/uscode/text/26/48E, read 2026-10-20; see docs/REVENUE_STREAMS.md.
- Note: A cost-side toggle, off by default, used only in the break-even column and the optional model confidence; it lowers the installed cost by the credit. ### model.yaml: area_error

- Value: p90={assessor: 0.63, assessor_below_footprint: 0.93, assessor_above_footprint: 0.93, footprint_x_stories: 0.93, footprint_only: 0.71}
- Source: docs/DATA.md, Footprint area error, "After site pooling and the area checks", measured 2026-10-19 on pilot candidates: the assessor source against LBER floor area (1,916 buildings, p90 63 percent), and footprint_x_stories (8,119 sites, 93) and footprint_only (9,284 sites, 71) at site level against BLD_AREA.
- Note: An estimated building's area is drawn as a lognormal around its stored area with sigma = ln(1 + p90 error) / 1.645, so about 90 percent of draws fall within the measured error. The error was measured only where BLD_AREA exists, so the real error on parcels missing it may be larger. Buildings with measured electricity get no area draw. No pilot site has an unknown utility; such a site would not be scored.
